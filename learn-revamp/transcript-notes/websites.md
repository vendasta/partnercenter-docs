## Date unknown — Maulin R (Vendasta web dev) with Daniel Gross (partner) — WooCommerce + Stripe subscription setup and Divi custom product-page design
**Source:** [CALL] `woocommerce-stripe-product-page-design-daniel-gross.txt` — a working session connecting Stripe to a WooCommerce site and attempting to give one tiered subscription product ("Ignite") a fully custom Divi-built landing page while keeping WooCommerce checkout intact.

4. **Platform-architecture nuance surfaced mid-call:** the partner's stack also included "Rapid Recovery," an acquired product folded into the WordPress environment but actually running on a *separate backend server* from the main WordPress/WooCommerce site — worth knowing when troubleshooting where a client's catalog data actually lives, since it looks/feels like native WooCommerce but isn't hosted the same place.
5. **The core design gotcha — pasting raw external HTML breaks the site:** the partner had an AI-generated (Claude) HTML/CSS mockup of a polished pricing-tier page (drop shadows, hover states, a specific black/blue/orange color scheme) and wanted it dropped in as-is. 8. **File-format gotcha:** Divi's native import/export (the "Portability" icon inside the Divi Builder) only accepts Divi's own proprietary shortcode-based layout format — not arbitrary AI-generated JSON, even when explicitly prompted to produce something "Divi-compatible." Attempting to import an AI-fabricated JSON file threw: *"This file should not be imported in this context."*
9. **Responsive-design gotcha:** a custom HTML/CSS Code module built outside Divi's grid system does not inherit Divi's built-in responsive breakpoints — confirmed live that the custom-styled product looked right on desktop but broke badly on mobile.
10. **Billing boundary flagged plainly by the dev:** ongoing requests to hand-code increasingly complex custom page layouts (rather than standard template edits) fall outside the base scope and would require the partner to purchase additional billable hours — stated upfront so it wasn't a surprise later.
11. **Practical scoping approach used on the call:** get exactly one tier ("Ignite") fully working end-to-end — custom design plus a functioning Stripe checkout — as a template/proof point, then replicate the same pattern across the remaining tiers rather than building/debugging all of them at once.

## Date unknown — Emily Portinari, Maulin R (Vendasta) with Hope Prost (client) — DMARC-blocked contact-form email, early diagnosis call
**Source:** [CALL] `dmarc-email-domain-troubleshooting-harvard-western-hope.txt` — first of two related calls diagnosing why a client's WordPress contact-form emails stopped delivering after a hosting migration.

## Date unknown — Nathan Tuplin, Taylor Balfour (client's IT/Microsoft 365 admin) with Maulin R (Vendasta) — DKIM/SPF/DMARC fix via Microsoft 365 + Fluent SMTP, plus DNS A-record cutover
**Source:** [CALL] `dns-dkim-spf-email-deliverability-harvard-western.txt` — the technical follow-up call with the client's IT admin, resolving the same DMARC email-delivery issue diagnosed in the companion call above.

1. **Diagnosis confirmed live:** DKIM records had been added for the domain, but outbound mail (sent via SendGrid, the site's transactional-email relay) was signing DKIM using **`sendgrid.net`** as the signing domain instead of the client's own domain — meaning DKIM alignment failed regardless of the DNS records being present, so DMARC failed and the client's mail server rejected inbound mail with a **550 bounce**.
2. **Why SPF alone wasn't the fix:** adding the entire SendGrid IP range to the domain's SPF record was explicitly rejected by the client's IT admin as a security risk ("we don't want to whitelist an entire SendGrid infrastructure... and you have no way to do modern auth to their tenant"). Key technical point volunteered by IT: DMARC only requires **one** of SPF or DKIM to align properly, not both — so a correctly DKIM-signed message (signed as the actual sending domain) would pass DMARC even without SPF covering SendGrid.
3. **Actual fix implemented:** move off SendGrid entirely for this mail flow and send through the client's own **Microsoft 365 tenant** instead, using the **Fluent SMTP** WordPress plugin configured for OAuth ("modern auth"). Steps: IT registered an Azure AD **App Registration** (Client ID, Client Secret, redirect/callback URL), granted the specific Microsoft Graph API permissions Fluent SMTP needs (primarily **Mail.Send**), and admin-approved the resulting consent request; the WordPress dev then configured Fluent SMTP with those credentials so outgoing site mail authenticates and sends as the client's own domain.
4. **Verification:** a live test email sent through the new configuration succeeded and showed up correctly in the Microsoft 365 "Sent Items" (traceable from the Exchange side), confirming DKIM would now sign correctly as the real domain.
5. **Separate DNS cutover handled on the same call:** the site's **A record** and **CNAME** (for `www`) were updated to point to the new WP Cloud hosting IP — flagged with a **24-hour TTL**, meaning propagation would take time; the dev's follow-up checklist item was to reconnect SSL to the new IP once DNS had propagated.
6. **Practical lesson:** DKIM/SPF/DMARC troubleshooting for a migrated site needs to check not just whether DNS records exist, but which **domain they're actually signing as** — a correctly-configured-looking DKIM record can still fail alignment if the mail relay signs under its own domain instead of the client's.

## Date unknown — Bill O (Vendasta) with Ajinkya K, Patrick Moran (Nova Scotia), Jennifer, Glen, Joanne Caruso, Allan Langille and other RCMP VA volunteers — formal WordPress/Divi training for a nonprofit multisite
**Source:** [CALL] `wordpress-training-rcmp-veterans-association-volunteers.txt` — a live training session teaching non-technical volunteer board members to manage posts/categories across the RCMP VA multisite.

1. **Multisite architecture explained:** rcmpva.org is the parent/top-level site; the Foundation, Ottawa, Nova Scotia, and (soon) Vancouver sites are all "child sites" underneath it. Access is scoped per-site — a division volunteer typically sees only their own division's site in the site picker, not the whole network — and provisioning access requires coordination between the Vendasta web team and the org's internal IT admin.
2. **Post-creation workflow demoed live:** Add New Post → Title → for content sourced from an external document, either (a) convert to PDF and upload via Add Media, then link using the **relative path** starting at `/wp-content/...` rather than a full absolute URL (a relative link only resolves on that same site and won't get redirected elsewhere), or (b) paste text directly using **Paste as Plain Text (Ctrl+Shift+V)** specifically to strip inherited Word/Google Docs formatting that would otherwise contaminate site-wide CSS consistency.
3. **Multi-category assignment:** a single post can carry more than one category simultaneously (e.g., both "In the News" and "Past Events" for a fundraiser recap), which is how the same content becomes discoverable in more than one place without duplicating the post.
4. **Meta description guidance:** manually filling in a post's meta description controls what Google's search snippet shows — a post consisting only of an embedded PDF with no meta description gives Google nothing useful to display, so even a one-sentence manual summary is worth adding.
5. **Publish-date mechanic used deliberately:** setting a custom publish date lets staff backdate a post to a meaningful real-world date (e.g., dating an in-memoriam post to the actual date of the member's passing) so entries sort correctly by real-world chronology rather than by data-entry date; the same field can schedule a post to appear in the future.
6. **SEO heading rule:** never start body content at Heading 1 — H1 is reserved for the page/SEO title; use Heading 2 and below within the content itself.
7. **Plain-language terminology used to teach non-technical volunteers** (worth reusing in Learn tab content aimed at similar audiences): a website is just folders of pages/media rendered through a browser via HTML; WordPress is a "website builder" CMS used by roughly 60% of websites; Divi is the specific theme/page-builder providing a flexible, module-based ("image module," "text module," "sidebar module") WYSIWYG layout system, versus more rigid off-the-shelf themes (explained with a house-framework analogy: framework = fixed room layout, theme = how it's finished/decorated).
8. **"Last Post" (in-memoriam) feature:** implemented as a responsive template (different layout on mobile vs. desktop/tablet); each division can choose its own cadence — one shared page updated repeatedly, or individual dated posts per person — as long as the visual template stays standardized across divisions.
9. **Bulk historical-content reality check:** one division (Vancouver, per a related call) had a backlog of roughly **1,900 legacy articles**; a peer division (Nova Scotia) also had a large backlog explicitly described as "astronomical" in projected hours if migrated manually by Vendasta staff — the practical resolution in both cases was training the client's own volunteers to self-serve the bulk upload rather than paying for it as billable services.
10. **Content-cap mechanic:** past events are capped to a configurable display count on the live page (e.g., showing the 3 most recent, expandable to 12 or more); anything beyond that display cap isn't deleted — it remains permanently reachable via on-site search/archive.
11. **Calendar-embed mechanic:** once granted account access to a division's external calendar (Google or Microsoft), the dev team pulls an **embed code** into the site so new calendar events populate automatically without manual post entry — access requests can get lost in email threads, so the recommended fix is resending the same thread with the correct dev team members freshly CC'd rather than starting a new one.
12. **Photo-gallery feature request:** requested for things like a photo contest; dev's recommendation was to build it as its own dedicated static page with a proper Divi gallery module (thumbnail grid with captions) rather than as a blog post, since a post/blog format only supports one image at a time in a next/previous flow, not an all-at-once grid.
13. **Training-delivery practice:** because live 1:1 training is billable/time-costly to repeat across many small nonprofit chapters, the recording gets cut into short, bite-sized topic clips (e.g., "how to schedule a post," "how to embed a PDF") for reuse across chapters instead of re-running full live walkthroughs each time.
